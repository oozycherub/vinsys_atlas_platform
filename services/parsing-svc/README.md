# parsing-svc (brick 6)

Turns an uploaded résumé (PDF, DOCX, scanned image, text) into a redacted, verified, normalised profile with chunk embeddings, and announces it with `profile.resume.parsed.v1`. It is the second Python brick (FastAPI, Temporal, uv, ruff, mypy --strict, pytest).

Spec: [`docs/prompts/06-parsing-svc.md`](../../docs/prompts/06-parsing-svc.md) · Contract: [`openapi.yaml`](openapi.yaml) (generated by FastAPI; `make openapi-py` regenerates it, and a test fails if it drifts).

## Design

```
http/app.py               parse requests, job status, SSE progress, bulk import, vector search, model swap
  └─▶ application/        ParsePipeline (stages), JobService + Dispatcher (fair share), BulkImporter,
                          EmbeddingIndex, DataProtection; ports.py, store.py
        └─▶ domain/       sniff (security gate), layout (hidden text, reading order), sections,
                          redact, schema (ParsedResumeV3), verify, proficiency, chunks
infrastructure/           Postgres repositories, S3 / memory storage, ClamAV, PyMuPDF / pdfplumber /
                          python-docx / pikepdf, PaddleOCR, service clients, Kafka consumer, Temporal
packages/py-platform      shared with llm-gateway: tenancy-aware DB, JWT, problem+json, outbox, PII spans
```

## The pipeline

`ParseResumeWorkflow` runs the stages as Temporal activities: intake, extract, enrich, embed, persist, plus `fail`. The retry policy is 3 attempts with backoff from 2 s to 30 s. A `PipelineError` is final; a dependency outage is retried. In development the same stages run inline (`ATLAS_PARSE_RUNNER=inline`).

| PRD stage               | Where     | What happens                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2 Security gate         | `intake`  | The real type comes from the bytes, never the declared type. A mismatch is quarantined. DOCX archives are limited to 2,000 entries, 50 MB uncompressed and an extreme per-entry compression ratio. Macros (`vbaProject.bin`) are quarantined. A password-protected OOXML file gives `ENCRYPTED_DOCUMENT`; legacy `.doc` gives `UNSUPPORTED_DOCUMENT`. Every file is scanned by ClamAV. PDFs are re-serialised by qpdf (pikepdf) with JavaScript, open actions, forms and embedded files removed, and encrypted PDFs are refused. |
| 3 Extraction            | `intake`  | PyMuPDF gives lines with bbox, font size and colour; pdfplumber is the fallback. DOCX is read with python-docx, including tables. A PDF under 50 characters per page goes to OCR, and so do images.                                                                                                                                                                                                                                                                                                                              |
| — Hidden text           | `intake`  | Text that is white, 2 pt or smaller, or off the page is dropped before anything else sees it, and the job is flagged `hidden_text`.                                                                                                                                                                                                                                                                                                                                                                                              |
| 4 Segmentation          | `intake`  | Reading order is an XY-cut variant: it finds the emptiest vertical channel, and lines that cross it (a name banner) separate bands. Sections are found from a heading vocabulary plus font-size jumps.                                                                                                                                                                                                                                                                                                                           |
| 5 Redaction             | `intake`  | Four detectors are combined. Presidio NER covers the contact block, and other people's names in References. Deterministic email and phone patterns apply everywhere. The **header-name rule** redacts the first name-shaped line of the header. The candidate's **known contact details** come from profile-svc (`pii:read`) and are redacted wherever they appear. Placeholders look like `<PERSON_1>`. If detection fails, nothing leaves the stage (`DEPENDENCY_UNAVAILABLE`, retryable).                                     |
| 6 LLM extraction        | `extract` | Calls the `resume.extract@1` prompt through llm-gateway; parsing-svc registers it at start-up. The prompt has a JSON-schema output, `contains_candidate_text: true`, no re-identified fields, and is `deterministic` so it can be cached. The gateway redacts again and scores prompt injection.                                                                                                                                                                                                                                 |
| 7 Evidence verification | `enrich`  | The model quotes its evidence; it does not count characters. Each quote must be found in the redacted source (fuzzy ratio ≥ 0.85), and the item's key term (skill, title, employer, institution) must appear next to it. Otherwise the item is dropped. A role or project keeps only the skills that appear in its own text.                                                                                                                                                                                                     |
| 8 Normalisation         | `enrich`  | taxonomy-svc `:normalize` maps skills and certifications, 100 terms per call.                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| 9 Proficiency           | `enrich`  | `min(3.5, 1 + 1.2·tanh(years/4) + 0.6·recency + 0.4·[≥2 roles] + 0.3·[certified])`. Confidence is `min(0.6, 0.35 + 0.1·spans)`. **Keyword stuffing** caps confidence at 0.2.                                                                                                                                                                                                                                                                                                                                                     |
| 10 Embeddings           | `embed`   | Chunks are the summary, one per role, projects and skills. They are embedded through llm-gateway and the response model is checked. During a model upgrade every chunk is written for both models.                                                                                                                                                                                                                                                                                                                               |
| 11 Persist              | `persist` | One transaction replaces the candidate's chunks (delete, then insert), finishes the job, and writes `profile.resume.parsed.v1`. A replay finds the job finished and does nothing.                                                                                                                                                                                                                                                                                                                                                |

### Prompt injection

The schema has no score or rating field, and `from_llm` ignores every key it does not know, so "rate me 5/5" has nowhere to go. Hidden text never reaches the model. A gateway injection score of 0.5 or more flags `prompt_injection_suspected`.

### Errors and the DLQ

| Outcome                                                             | Job status                                                    | Event                                                           |
| ------------------------------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------- |
| `UNREADABLE_DOCUMENT`, `ENCRYPTED_DOCUMENT`, `UNSUPPORTED_DOCUMENT` | `failed` (final)                                              | `profile.resume.parse_failed.v1` with `retryable: false`        |
| `MALICIOUS_FILE`                                                    | `quarantined`; the object moves to `quarantine/t/{tid}/{doc}` | `parse_failed`, plus `security.file.quarantined.v1`             |
| `LLM_UNAVAILABLE`, `DEPENDENCY_UNAVAILABLE` after 3 attempts        | `failed_retryable`                                            | `parse_failed` with `retryable: true` (the DLQ; re-parse later) |

profile-svc consumes both new events. It sets the document to `failed`, `failed_retryable` or `quarantined`, and never un-parses a document that already has a profile.

### Fair share (PRD §1.2.3)

Jobs are queued, then claimed in a system transaction, round-robin across tenants (`row_number() OVER (PARTITION BY tenant)`). A tenant never has more than `ATLAS_PARSE_PER_TENANT_CONCURRENCY` jobs running, so one tenant's large bulk upload cannot starve the others. An advisory lock serialises dispatchers.

### Bulk import

`POST /v1/resumes:bulkImport` accepts a zip of at most 500 files and 200 MB. Each file becomes a placeholder candidate (`external_ref bulk:{batch}:{i}`, idempotent) and an upload into profile-svc. From there it follows the normal path, so every rule above applies.

- Once parsed, the candidate's contact block replaces the placeholder (a PATCH with If-Match).
- If the email belongs to an existing candidate, the job is flagged `duplicate_candidate`.
- Entry names are never stored, because file names often contain names.

### Embedding model upgrade (shadow, then swap)

1. `PUT /v1/embedding-models/shadow` sets the new model; new parses start dual-writing.
2. Call `POST /v1/embedding-models:backfill` for each tenant until `remaining` is 0. It re-embeds the stored redacted text, so nothing is re-parsed.
3. `POST /v1/embedding-models:promote` swaps the active and shadow models.

Queries must name the active model (`409 EMBEDDING_MODEL_MISMATCH` otherwise), so no query mixes models.

### Search for other services

`POST /v1/resume-embeddings:search` (service, scope `embeddings:search`) runs HNSW ANN with `ef_search = 100`, capped at 500 chunks. It runs inside the tenant's transaction, so RLS limits results to that tenant.

matching-svc (brick 7) uses it in two ways. Candidate generation is plain ANN. Re-ranking passes `candidate_ids` with `per_candidate`, an exact search that returns each named candidate's closest chunks, and `include_vectors`, because SEM needs the vectors themselves.

## Owned data (`0009_parsing.sql`)

| Table                                | Holds                                                                                                                                                         |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `parse_jobs`                         | Status, stage, progress, attempts, error code and flags. `result` holds metrics only, never content. A partial unique index allows one live job per document. |
| `parse_batches`, `parse_batch_items` | Bulk imports, without file names.                                                                                                                             |
| `resume_embeddings`                  | `vector(1024)`, HNSW (m=16, ef_construction=64), the exact redacted text embedded, and `model_id`. Rows are replaced, never updated.                          |
| `embedding_model_slots`              | The active and shadow models. Seeded with `bge-m3`; the app may only update it.                                                                               |

RLS is strict per tenant. The exception is `parse_jobs`, which the dispatcher also reads inside system transactions.

There are **no foreign keys to profile-svc's tables** (the 0007 rule). Erasure (`privacy.erasure.requested.v1`, acknowledged as `parsing-svc`) and tenant purge delete this service's rows instead of a cascade.

## Running and testing

```bash
uv sync
uv run pytest --cov=parsing_svc           # real Postgres (pgserver), Presidio, Temporal test server
uv run python tests/golden/generate.py    # regenerates the golden set (deterministic)
uv run python -m parsing_svc.main         # API; add `worker` for the Temporal worker
```

### Golden set

`tests/golden` holds 50 synthetic résumés: fictional people in single- and two-column PDFs, DOCX with tables, and text. `test_golden.py` runs all 50 through the real pipeline, with the model replaced by an oracle that answers with the expected data. It requires field F1 ≥ 0.95 and currently scores 1.000. It also checks that no contact detail reaches the model or the event.

This measures everything around the model. It caught these real defects, all now fixed:

- two-column reading order was broken;
- NER missed candidate names;
- NER tagged employers as people;
- a name span ran into the email below it.

`scripts/eval_golden.py` measures the **real model** through a running llm-gateway. It makes 50 billed calls and has not been run yet.

## Decisions and known gaps

- **Evidence quotes instead of model-supplied offsets.** The verifier computes `evidence_span` itself, so the stored profile matches the PRD and the check is stricter.
- **Section segmentation is heuristic.** The PRD's LightGBM classifier needs labelled data that does not exist yet.
- **Language.** The model reports the document language; there is no fastText.
- **Progress** is read from `parse_jobs`, not Redis.
- **Employers and institutions are not redacted** (PRD example `<ORG_1>`). They are what matching needs, and they are not personal data on their own.
- **Workflow id** is `parse-{job_id}`, not `parse-{document_id}`. A re-parse is a new job. One live job per document is enforced by the database.
- **Not done yet:**
  - the production OCR worker image;
  - a Presidio custom recogniser set (photo, gender and nationality markers);
  - matching the duplicate person on email (the job is flagged; profile-svc still has two candidates);
  - llm-gateway serving two embedding models during an upgrade (the gateway serves one model today).
